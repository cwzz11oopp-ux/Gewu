# Unified Experiment Code Generation and Remote GPU Execution Design

## Goal

Make real experiments executable without requiring the user to hand-write `train.py`.
The workflow must use the existing `experiment-bridge` Skill to generate experiment
code, then run that generated code through either `local_gpu` or SSH-backed
`remote_gpu`.

This design also verifies that remote GPU settings entered in the frontend are
actually persisted to the backend and are sufficient for a real SSH execution.

## Current State

The runtime already routes the `experiment_task` step to `experiment-bridge`.
However, `ExperimentAgent.build_task()` only calls `ExperimentProvider.plan()`.
The loaded Skill instructions constrain planning, but they do not currently
produce executable code.

Local execution currently expects this pre-existing file:

```text
LOCAL_EXPERIMENT_WORKDIR/train.py
```

Remote execution currently expects this pre-existing file:

```text
REMOTE_GPU_PROJECT_DIR/experiments/train.py
```

The frontend remote settings form already captures host, user, port, SSH key
path, project directory, Python command, CUDA devices, and timeout. These fields
are posted to `/api/settings/experiment`, normalized in `RuntimeConfigStore`,
applied into `Settings`, and used by `RemoteGpuExperimentProvider`. The missing
piece is real connection validation and code deployment.

## Non-Goals

- Do not add a new Skill if the existing `experiment-bridge` Skill can supply
  the code-generation contract.
- Do not execute arbitrary generated shell scripts.
- Do not install dependencies automatically on local or remote machines.
- Do not overwrite files outside the configured experiment project directory.
- Do not claim remote GPU readiness from field presence alone.

## Proposed Flow

The workflow gains a generated experiment-code artifact between experiment task
planning and experiment execution:

```text
research_plan
-> experiment_task
-> experiment_code
-> provider deploy
-> provider run
-> experiment_result
```

`experiment_code` is generated by Qwen using:

- the normalized research plan,
- the experiment task,
- the loaded `experiment-bridge` Skill instructions,
- a strict output schema.

The provider layer does not decide scientific content. It only deploys and runs
the already-generated code.

## Experiment Code Artifact Contract

The generated artifact must have this shape:

```json
{
  "entrypoint": "train.py",
  "files": [
    {
      "path": "train.py",
      "content": "..."
    }
  ],
  "command": "python train.py --seed 7 --output results/run_seed_7.json",
  "metrics_path": "results/run_seed_7.json",
  "log_path": "logs/run_seed_7.log",
  "assumptions": ["..."],
  "validation": {
    "requires_network": false,
    "expected_metrics": ["accuracy", "loss"]
  }
}
```

Rules:

- `entrypoint` must be `train.py` for the first implementation.
- Each file path must be relative, normalized, and must not contain `..`.
- `command` must invoke the configured Python command plus `train.py`.
- `train.py` must accept `--seed` and `--output`.
- `train.py` must create the output parent directory.
- The last stdout line must be parseable JSON.
- Metrics must be produced by real computation, not hard-coded placeholders.
- Network access is not assumed. Generated code should prefer local or bundled
  toy datasets unless the plan explicitly requires an already-available dataset.

## Local GPU Behavior

For `local_gpu`, the provider deploys files under:

```text
LOCAL_EXPERIMENT_WORKDIR
```

Execution uses:

```text
cwd = LOCAL_EXPERIMENT_WORKDIR
<LOCAL_GPU_PYTHON> train.py --seed ... --output ...
```

The provider records:

- deployed file paths,
- resolved workdir,
- command,
- metrics path,
- log path,
- stdout tail and stderr tail on failure.

If `LOCAL_EXPERIMENT_WORKDIR` does not exist, the provider returns
`LOCAL_EXPERIMENT_WORKDIR_INVALID`. The directory must exist before deployment;
the system should not silently create an arbitrary local path.

## Remote GPU Behavior

For `remote_gpu`, the provider deploys files under:

```text
REMOTE_GPU_PROJECT_DIR
```

The provider uses SSH to:

1. create controlled subdirectories such as `results/` and `logs/`,
2. write generated files into `REMOTE_GPU_PROJECT_DIR`,
3. run the generated command from `REMOTE_GPU_PROJECT_DIR`,
4. stream/save logs,
5. read the metrics JSON from stdout or `metrics_path`.

The generated command should be relative to the remote project directory:

```text
<REMOTE_GPU_PYTHON> train.py --seed ... --output results/run_seed_7.json
```

Remote deployment must reject paths outside `REMOTE_GPU_PROJECT_DIR`.

## Remote Settings Validation

The frontend already sends remote SSH fields to the backend. The backend must
upgrade `/api/settings/experiment/test` for `remote_gpu` from a field-presence
check to a real SSH readiness check.

Validation steps:

```text
ssh -p <port> [-i key] user@host "mkdir -p <project_dir> && test -w <project_dir> && cd <project_dir> && <python> --version"
```

If CUDA devices are configured, an optional check may run:

```text
CUDA_VISIBLE_DEVICES=<devices> nvidia-smi
```

The response must be structured:

```json
{
  "ok": false,
  "provider": "remote_gpu",
  "code": "REMOTE_GPU_SSH_FAILED",
  "host": "...",
  "user": "...",
  "port": 22,
  "project_dir": "...",
  "missing": [],
  "stdout_tail": "...",
  "stderr_tail": "...",
  "message": "..."
}
```

Relevant error codes:

- `REMOTE_GPU_CONFIG_MISSING`
- `REMOTE_GPU_SSH_FAILED`
- `REMOTE_GPU_PROJECT_DIR_INVALID`
- `REMOTE_GPU_PROJECT_DIR_NOT_WRITABLE`
- `REMOTE_GPU_PYTHON_INVALID`
- `REMOTE_GPU_CUDA_UNAVAILABLE`

Saving remote config may still save field-complete settings without requiring a
successful SSH test, but provider status must distinguish configured from
verified if the test has not been run.

## Backend Components

### ExperimentAgent

Add code generation responsibility:

- `build_task(plan, instructions)` continues to create the experiment task.
- `generate_code(plan, task, instructions)` calls `LLMProvider.generate_json()`
  and returns the normalized `experiment_code` artifact.

The agent validates the schema before the workflow saves it.

### WorkflowEngine

When running `experiment_task`, save both:

1. `experiment_task`
2. `experiment_code`

When running `experiment_run_analysis`, pass the latest `experiment_code` to the
provider along with the task. This keeps rerun behavior explicit and auditable.

### ExperimentProvider Protocol

Extend provider behavior to support generated code deployment:

```python
def run(self, task: dict, code: dict | None = None) -> dict: ...
```

Existing tests using `run(task)` should keep working by treating `code=None` as
legacy behavior during migration.

### LocalGpuExperimentProvider

Implement deployment of `code["files"]` to the local workdir before execution.
Keep the existing `train.py` path validation for legacy behavior when no code
artifact is supplied.

### RemoteGpuExperimentProvider

Implement remote deployment through SSH. The first implementation can write file
contents by sending a Python file-writer program over SSH stdin or by using a
portable shell-safe transfer mechanism. It must avoid brittle quoting of large
generated code inside a one-line SSH command.

## Frontend Behavior

The settings modal should show remote test diagnostics:

- missing fields,
- SSH failure,
- remote project directory,
- Python version result,
- stderr tail when SSH fails.

The user should be able to tell whether remote settings were merely saved or
actually verified.

## Testing Strategy

Backend tests:

- `experiment_task` saves an `experiment_code` artifact when Qwen/mock returns
  valid generated code.
- Invalid generated file paths are rejected.
- Local provider deploys generated `train.py` and executes it from the configured
  workdir.
- Remote provider builds SSH commands from frontend-saved settings.
- Remote provider deploys generated files under `REMOTE_GPU_PROJECT_DIR`.
- Remote settings test reports missing fields without SSH.
- Remote settings test reports SSH command failure with structured diagnostics.
- Runtime config preserves remote fields from frontend save.

Frontend/build tests:

- `ExperimentTestResult` and provider status types include remote diagnostic
  fields.
- Settings modal can render remote diagnostic fields without type errors.

Manual verification:

- Save remote settings from the frontend.
- Call `/api/settings/providers` and confirm the values are active.
- Run remote config test against a known SSH target.
- Run a generated smoke experiment locally.
- Run the same generated smoke experiment remotely when SSH is available.

## Risks and Mitigations

- Generated code may be unsafe or destructive.
  Mitigation: restrict paths, forbid shell scripts for the first version, and run
  only generated Python entrypoints under configured workdirs.
- Generated code may require unavailable packages.
  Mitigation: Skill instructions should prefer standard-library or already
  installed dependencies for smoke experiments; failures return structured
  diagnostics for revision.
- SSH deployment may break on quoting.
  Mitigation: use stdin/file-transfer style deployment instead of embedding file
  content in remote shell strings.
- Remote readiness may be slow.
  Mitigation: keep config tests timeout-bounded and return clear tails.

## Acceptance Criteria

- The system can generate a `train.py` artifact from the experiment plan and
  `experiment-bridge` instructions.
- `local_gpu` can deploy and run the generated code without pre-existing
  `train.py`.
- `remote_gpu` can deploy and run the generated code over SSH without
  pre-existing `experiments/train.py`.
- Frontend remote SSH settings are persisted into backend runtime settings.
- Remote config testing performs a real SSH/Python/project-dir check and returns
  structured diagnostics.
- Existing mock workflow and report export guards continue to pass.
